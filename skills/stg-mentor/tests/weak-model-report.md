# 弱模型仿真验证报告 · Steps2Great-skill

> **测的是什么**：把 StepsToGreat 封装成通用 Agent Skill 之后，**弱模型还能不能照做**。
> 上游 StepsToGreat 已经测过「协议本身对弱模型够不够明确」（12/12，见其 `docs/weak-model/`）。
> 本次要测的是**封装层新引入的风险** —— 那是上游测不到的：
> ① 模型能不能**自主发现并加载** skill（而不是等用户点名）？
> ② 加载后能不能**正确定位** skill 里的 `references/` 与 `scripts/`？
> ③ 在工作区里建目录、写档案时，**路径口径**会不会串（skill 目录 vs 学生工作区）？
> ④ 封装后的 `validate-state.mjs` 还准不准？
>
> **测试日期**：2026-09-22　**框架版本**：1.0.0
> **任务卡与判分器**：[`../_build/score-workspace.mjs`](../_build/score-workspace.mjs)｜[`tests/regression-state.mjs`](tests/regression-state.mjs)

## 3. 弱模型当探针：抓到的 3 个真缺陷（已修 + 已钉回归）

> 这一节才是本次测试的核心。弱模型「不会猜」，于是**诚实标注**和**格式变体**都被它踩了出来。
> 关键判据：**若模型的写法是合理的，而校验器判它失败，那是校验器的 bug，不是模型的错。**

### 3.1 🔴 I11 有个时序缺口：未标「已掌握」的课，重复小节永远查不到

**谁发现的**：DS-OFF 自述第 5 节，且**它自己 grep 小节标题才发现** —— 校验器当时报 PASSED。

**根因**（我读代码确认并复现）：I11 被写在 `isMastered()` 循环**内部**：

```js
for (const m of mastery) {
  if (!isMastered(m.status)) continue;   // ← 未标已掌握就直接跳过
  ...
  const dups = checkDuplicateSections(answerText);  // ← I11 在这里
}
```

后果：一份回答文档已经出现**两份「最终复评结果」**（正是 I11 想拦的「同一信息写多处」），
只要 📊 里对应行还是 `⏳ 待作答`，校验器**照样 PASSED**。

**我构造的最小复现**（`tests/regression-state.mjs` T1）：

| 输入 | 修复前 | 修复后 |
|---|---|---|
| 回答文档：2×「最终复评结果」+ 2×「正确答案与解析」+ 残留占位<br>📊：「⏳ 待作答」 | **PASSED**（退出码 0）❌ | **FAILED** ✅ |

**修复**：把 I11 提成**独立段落**，扫全部回答文档（📚 索引登记的 + 磁盘上实际存在的），
与「是否已声明掌握」彻底解耦 —— 同一文档出现两份复评区就是错的，无论掌握表写了什么。

> I11 是**上游那次弱模型测试专门加的**（GLM 写了两份互相矛盾的复评区）。
> 也就是说：**上一次弱模型测试发现的缺陷，其修复本身又有一个盲区，而这次被更弱的模型踩出来了。**

### 3.2 🔴 I6 会误报：备注写「证据：\`路径\`（说明）」被判成「证据文件不存在」

**谁发现的**：GLM-LOW 与 FLASH-LOW 独立踩到同一坑，两个都改了写法才通过。
GLM 的自述原话：「校验器 I6 要求 📊 备注第一段是裸路径（反引号或『证据：』前缀会黏进路径导致误报）——
**这是试错摸出的隐含格式，协议没写**。」

**根因**：`linkTarget()` 取「按分隔符切出的第一段」当路径：

```js
const raw = m ? m[1] : cell.split(/[；;，,\s]/)[0];
if (!m && !/\/|\.md$/i.test(cleaned)) return undefined;  // 「像路径」就算路径
```

面对这个真实单元格：

```
证据：`我的学习/学科/Python/01-变量/01_学生回答.md`「最终复评结果」（2 处代改 + 1 次追问换 2 角度讲通）
```

切出的第一段是 `证据：\`我的学习/学科/Python/01-变量/01_学生回答.md\`「最终复评结果」（2`
—— 它**含有 `/`**，于是通过了「像不像路径」的检查，却根本 resolve 不出来 → 误报 I6。

**修复**：改成优先**抠出以 `.md` 结尾的路径本身**（两种真实写法都认），而不是取第一个片段。

| 输入 | 修复前 | 修复后 |
|---|---|---|
| 备注 = `证据：\`<路径>.md\`「最终复评结果」（说明）` | **FAILED**（误报证据不存在）❌ | **PASSED** ✅ |

> 这条特别值得记：**三个模型里有三个都写了这种人类读起来完全正常的备注，全被判失败。**
> 判据本身错了 —— 校验器应该宽容「人怎么自然地写」，而不是要求一种没写进协议的格式。

### 3.3 🔴 I3 会惩罚诚实：🚦 里写「（待建，学生作答后创建）」被判成「指向不存在的文件」

**谁发现的**：GLM-LOW 的**路由测试**（只走到摸底阶段）。它在 🚦 的「回答文档」栏写：

```
我的学习/学科/Python/00-摸底测试.md（待建，学生作答后创建）
```

**这是完全正确的行为** —— 摸底阶段那份文档确实还没建，它**诚实地标注了原因**。
但校验器把整串当路径，resolve 失败 → 判 `[I3] 指向不存在的文件` → **FAILED**。
FLASH-LOW 的写法是 `待发布（摸底通过后建 我的学习/…）`，同样被判失败。

**修复**：识别「自述尚未创建」（`待建|待发布|尚未|未创建|未发布|作答后创建|not yet|pending`…）
→ 降级为**提示**，与 `03_落档事件表` §6 的「情形 A（尚未发布）」同一档。
并**加了反向用例 T7**（写了个不存在的路径但不自称待建 → 仍然 FAILED），防止放宽过度。

| 输入（🚦 的文档栏） | 修复前 | 修复后 |
|---|---|---|
| `…00-摸底测试.md（待建，学生作答后创建）` | **FAILED** ❌ | PASSED + 提示 ✅ |
| `待发布（摸底通过后建 我的学习/…）` | **FAILED** ❌ | PASSED + 提示 ✅ |
| `我的学习/…/根本不存在.md`（不自称待建） | FAILED ✅ | **FAILED** ✅（仍要拦） |

**修复时还踩了自己的一个坑**（记录下来当教材）：
第一版把「剥括号说明」写进了 `clean()`，结果 `clean()` 是**全局共用**的 ——
它把「（待建）」剥掉之后，`isPlaceholder()` 就再也看不到「待建」这个信息，修复根本不生效。
改成**分层**：`clean()` 保留信息，只有真要当路径解析时才由 `stripPathNote()` 剥掉。

### 3.4 加上第 4 个：🟠 模板里的框架链接，复制进工作区就是死链

**谁发现的**：GLM-5.2 —— 但**发现路径本身也暴露了我的另一个错误**。

它当时读的是**上游** `E:\StepsToGreat\模板\课程路线模板.md`（因为我把 skill 目录删了），
模板里写着 `../../../协议/00_导师协议.md`。它在**上游仓库里是对的**（上游的学习者就工作在仓库根，
`协议/` 确实存在），但 GLM-5.2 把它改成 `../../协议/…` 复制进工作区后 ——
**工作区里根本没有 `协议/` 目录**，于是留下 3 处死链。

**根因（比模型的行为更深）**：
`references/模板/` 是**给学生工作区用的脚手架**，模型会把它们复制成
`我的学习/学科/<学科>/00-课程路线.md`。但这些模板里的相对链接是按**上游仓库**写的，
**本 skill 的工作区里不存在框架目录** —— 复制过去必然死链。

**修复**（两层）：
1. `_build/sync-from-upstream.mjs` 新增 `defuseTemplateLinks()`：模板按各自的
   **虚拟目标位置**（如课程路线 → `我的学习/学科/<学科>`）重算链接：
   - **框架内部链接**（协议/学科包/模板/示例/教程）→ 改写成文字说明
   （「在 skill 的 references/ 下」），无论复制到哪都不可能变成死链
   - **工作区内部链接**（我的学习/…）→ 按目标位置**重算为正确相对路径**，保住可点性
   - **交叉引用另一个模板** → 映射到它在工作区里的**最终文件名**
   （`学生回答模板.md` → `01_学生回答.md`）
2. `scripts/check.mjs` 增加检查：模板里若还留着框架链接 → 直接报错

**验证**：把 4 个模板按模型的实际做法复制进一个真工作区，逐一查链接 —— **4 个链接、0 个死链**。

> **同时暴露出我自己的一次操作事故**（已修，见 §4.3）：我删 skill 目录时 GLM-5.2 还在跑。

### 3.5 🔴 第 5 个（最隐蔽）：跑一次 sync，把之前修好的 3 个缺陷**全冲掉了**

**怎么发现的**：我先修好了上面 3 个缺陷、回归测试 7/7 全绿；随后为了做模板链接改写跑了一次
`node _build/sync-from-upstream.mjs` —— **回归测试立刻变成 3/7 红**。

**根因**：`scripts/validate-state.mjs` 是从上游 `_tools/validate-state.mjs` **镜像**来的，
而我在它上面做了上游没有的修复。**「镜像目标」与「手改文件」是同一个文件** ——
每次 sync 都会静默覆盖手改内容。这类问题最危险的地方在于：**它没有任何报错**。

**修复（结构性，不只是补数据）**：
1. 把该文件标为 **skill 侧独占**（`SKILL_OWNED`）：sync 默认**跳过**它，不再覆盖；
   要重取上游版本必须显式 `--refresh-owned`。
2. 给 skill 独占文件登记**修复指纹**（`SKILL_OWNED_MARKS`），每次 sync **结束前断言**指纹还在；
   丢了就报错并 **`exitCode = 1`**（否则 CI 会静默放过）。
3. 新增 `tests/regression-sync.mjs`（4 个用例）把这件事钉住：
   - S1 正常 sync → 指纹完好、退出码 0
   - S2 强制覆盖 → sync **必须**报错并退出码 1
   - S3 覆盖之后 → 状态校验器回归**确实**变红（证明保护不是摆设）
   - S4 恢复之后 → 回归全绿

> **这条是本次测试最有价值的副产品**：它跟模型无关，是**封装工程本身的结构缺陷** ——
> 只要有「镜像 + 手改」两份来源，就一定有这个坑。现在它被显式建模、被断言、被 CI 看守。

### 3.6 五个缺陷的共同模式（值得记住的一句话）

> **校验器前三个缺陷都在「惩罚诚实、奖励特定格式」**：
> 模型写得越老实（注明「还没建」、备注里把证据和结论写在一起），越容易被判失败。
>
> 后两个则是**封装工程**的问题：**内容会移动，但链接是死的**；
> **文件会重生成，但手改是活的**。
>
> 判据应当是：**「模型的写法人类读起来对不对？」** —— 而不是「它有没有猜中我没写出来的格式」。

## 4. 各模型的表现与差异

### 4.1 它们都做到了什么（值得肯定）

| 观察 | 证据 |
|---|---|
| **零提示自主触发** | GLM/FLASH 都从「我想学 Python…」直接命中 skill，并去 skill 目录找到 `init-workspace.mjs` 跑通 |
| **按需读参考，不一次全灌** | GLM 路由测试只读了 `01_摸底剧本.md`；FLASH 读了协议+学科包+模板（未读的 5 份明确列出） |
| **路径口径没串** | 三个工作区的产出里**都没有**把 skill 的 `references/协议/…` 当成工作区路径写进产出（封装层专查 0 命中） |
| **轮次纪律零违规** | 三个模型 × 4 轮，无一处 >3 题，无一处分批发全课题 |
| **失败后能自纠** | FLASH 首跑 2 次真失败（I6/I7），自己改对再复跑；GLM 首跑也被 I6 拦过 |
| **诚实度** | DS-OFF 主动报告「任务说目录已初始化，实际不存在，是我自己建的」；GLM-5.2 主动报告「skill 目录不存在，我回退读了上游仓库」 |

### 4.2 值得单独记的三件事

**① DS-OFF 报了一个测试自身的问题**
任务卡说 `off-ds` 已预置，但**该目录当时确实还不存在**（我建工作区的命令与它启动并发，
它先跑了）。它没有报错停下，而是自己 `init-workspace.mjs` 建好再继续 ——
并且**在报告里明确指出这个不一致**。这说明 `init-workspace.mjs` 的幂等与「不覆盖」设计是有效的。

**② FLASH 撞出了协议的一个真空白**
它的 I7 二次失败原因：它在「最终复评结果」区**又放了一张表**（列是「问题/类型/处理方式」），
校验器把「处理方式」解析成维度列 → 判 I7「复评表里有非 ✅ 维度」。
**根因不是模型错**：协议没有规定「最终复评结果区只能有一张表」。
这条**未修**（改动面较大），列入 §5.1 的建议。

**③ 我自己的操作事故：删 skill 目录时 GLM-5.2 还在跑**
为了让工作区干净，我删掉了 `~/.dsh/skills/steps2great-skill` —— 但 GLM-5.2 当时仍在运行。
它没有失败，而是**明确报告**「skill 目录不存在，我回退到上游仓库 `E:\StepsToGreat`」。
- **好在**：它因此撞出了 §3.4 那个模板死链缺陷（它读的是上游模板）。
- **代价**：这一份数据不是干净的 skill 环境数据；同时它也导致我的跑分器一度因
  「找不到校验器」把 F 维判低（**那是跑分器的不稳定，不是模型的差异** ——
  已修：跑分器现在会回退到本仓库自己的校验器，见 §5.3）。
- **教训**：**测试期间不要改动被测环境**。清理动作要么在全部运行结束后做，要么先确认没有运行中的任务。

## 5. 结论

### 5.1 对封装本身的回答

| 问题 | 结论 |
|---|---|
| 弱模型能否**自主发现并加载**这个 skill？ | **能**（2/3）。触发层双语的 `description` 有效；但**有客户端可能根本不支持 skill**（Qoder 免费档） |
| 加载后能否**正确定位** skill 里的资源？ | **能**。全部 4 个符合性运行都正确读到了 `references/` 与 `scripts/`，路径口径零串线 |
| 在工作区里**建目录/写档案**是否可靠？ | **可靠**。4 个工作区结构一致，`init-workspace.mjs` 幂等且不覆盖学生资产 |
| 封装后的校验器还准不准？ | **一开始不准** —— 先后发现 **5 个真缺陷，全部已修 + 已钉回归测试**（状态 7 个用例 + 镜像 4 个用例） |

**修正后的结论**：**协议对弱模型是可用的（12/12 × 4）**，但封装层引入的缺陷必须修掉 ——
前 3 个（校验器）会持续给**完全正确的模型**打失败分，从而污染「协议够不够明确」的判断；
后 2 个（模板链接、镜像覆盖手改）是**封装工程自身的结构问题**，与模型行为无关，
但同样会静默产生错误结果。
这正是「弱模型当探针」的价值：它们不猜格式，所以格式问题与链接问题都无所遁形。

### 5.2 本次测试的缺口（必须诚实说明）

| 缺口 | 影响 |
|---|---|
| **GLM-5.2 无 off 档** | 用户点名的 `workbuddy/glm-5.2` 只提供 `high/xhigh`，**降不到不思考** —— 它跑完了，但不是「弱档」数据 |
| **GLM-5.2 那次运行被污染** | 我删 skill 目录时它还在跑，它回退读了上游 `E:\StepsToGreat`（§4.2③） |
| **只有 1 个模型跑到「真正 off」** | `off` 档只在 `lobsterai/deepseek-flash` 上可用；异家族模型（GLM）**最低只能到 low** |
| **每组样本量 = 4** | 结论是「未发现失败」，不是「保证不失败」 |
| **「能力」与「客户端」混杂** | Qoder 未触发**无法区分**是模型能力还是客户端不支持 skill |

### 5.3 建议

| 建议 | 理由 |
|---|---|
| **每次改协议后跑一遍 `npm test`** | 11 个用例（状态 7 + 镜像 4），把本轮 5 个坑全钉住了 |
| **改 `validate-state.mjs` 时先问「这会不会惩罚诚实写法？」** | 本次 3 个缺陷是同一个模式 |
| **跑 sync 后必须重跑回归** | `sync` 会覆盖手改文件 —— 这个坑已经踩过一次（§3.5），现在有指纹断言兜底 |
| **测试期间不要改动被测环境** | 我曾边跑边清理，污染了一份数据（§4.2③） |
| **把「复评区只应有一张表」写进协议** | FLASH 撞出的真空白（§4.2②），目前靠报错反推 |
| **在 README 里说明「若你的客户端不加载 skill，怎么手工用」** | Qoder 那类失败需要一条兜底路径 |
| **触发路由应纳入常规测试** | 它测的是「skill 到底会不会被用上」，和协议符合性同等重要 |
